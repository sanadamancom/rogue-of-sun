# Phase 02: ランダム1フロア生成

## フェーズの目的
Phase 01のターン制移動・近接戦闘を維持したまま、部屋と通路で構成された、シード再現可能なランダム1フロアを実装する。今回はマップ生成方式とカメラ追従の成立確認に限定する。

- local main / origin/main: 一致
- working tree: clean
- Phase 01既存テスト: 4ファイル20件全pass(開始時点で失敗なし)

## 採用した生成方式
部屋(重ならない長方形)+ 通路(1マス幅、水平/垂直区間のみ)方式。BSP・洞窟・WFCなど他方式は採用していない(out_of_scopeに準拠)。

- シード付き疑似乱数生成器: Mulberry32(32bit整数シードから決定論的な浮動小数列を生成)
- 部屋配置: ランダムな位置・サイズを試行し、既存部屋と重ならないものだけ採用(最大試行回数あり)
- 連結: 各部屋の中心点をノードとしたグラフに対しPrim法で最小全域木を構築し、そのエッジに沿って通路を掘る
- 追加接続: MSTに含まれないエッジのうち距離が近いものから1〜2本を追加し、環状経路を作る
- 生成失敗時の扱い: 部屋数が目標最小値に届かない場合は同一シードから内部試行カウンタをシードに混合して決定論的に再試行し、上限(50回)に達した場合は明示的な生成失敗として扱う(`generateMap`が`{ ok: false }`を返す)

## マップ生成手順
1. `createRng(seed)`でPRNGを生成
2. 目標部屋数(6〜9)を決定し、各部屋のサイズ(幅4〜9、高さ4〜7)と位置をランダムに試行、重なり判定に合格したものだけ採用
3. 全部屋を'wall'で埋めた地形配列に対して'floor'として彫る
4. 部屋中心点間のMSTを構築し、通路を彫る(水平→垂直、または垂直→水平のいずれかをランダムに選択、斜めなし)
5. MST外のエッジから1〜2本を追加接続として彫る
6. 開始地点(最初の部屋の中心)からBFSで全床マスへの距離を計算し、最も遠い部屋を出口部屋として選定
7. 開始地点・出口と重ならず、開始地点に隣接しない到達可能な床マスをランダムに1つ選び敵位置とする

## 主要な仕様判断
- 出口部屋の選定は「開始地点からのBFS距離が最大の部屋」とし、必ず開始地点と異なる部屋になる
- 敵配置は「開始地点・出口と別マスかつ開始地点に非隣接」という制約を満たす床マスからランダムに選択。制約を満たす候補がない極端なケースのみ出口マスへのフォールバックとしたが、実際のマップサイズ・部屋数では発生していない
- 生成失敗時の再試行は、外部状態(時刻・Math.random)を使わず、シードと試行回数を合成した値で新たなPRMを作ることで決定論性を保った
- 敵の追跡・戦闘ロジック(Phase 01のシンプル追跡)はそのまま維持し、置き換えは行っていない(著しい不具合が確認されなかったため)

# 追記: 通路並走接触の修正(phase-02-corridor-contact-fix)

## 問題
独立した通路同士が不用意に隣接・並走し、幅2マス以上の通路帯に見える箇所があった(ユーザー報告のスクリーンショットで確認)。

## 再現シードと問題座標
- 再現シード: `7`
- 問題座標: `(27,8)`〜`(27,10)`付近、`(14,15)`付近(修正前、部屋外の非部屋床タイルが2x2以上のブロックを形成)
- 3000シード(1〜3000)で走査した結果、481件(約16%)で同種の接触が発生していた

## 根本原因
各通路(MSTエッジ・追加接続エッジ)を、部屋中心点間のL字(水平→垂直 or 垂直→水平)でそのまま床化していた。個々の通路自体は幅1マスだが、複数の独立した通路が同じ行・列を偶然通ると、床化前に他の通路との位置関係を検証していなかったため、側面が接触して幅2マス以上の帯に見えるケースが生じていた。

## 採用した経路検証規則
- 事後に床を削除する方式は採用せず、通路を床化する**前**に候補経路を検証する方式へ変更した(`isRouteValid`)
- 候補経路(部屋中心点からのL字、水平→垂直/垂直→水平の2通り)の各非部屋タイルについて、4方向の隣接タイルを確認する
- 以下は「必要な接触」として許可する:
  - 部屋内部への隣接(出入口として必要)
  - 経路自身の前後・曲がり角のタイル(同じ通路内での隣接)
  - 既にそのタイル自体が床である場合(=既存通路との交差点。T字・十字の意図的な交差として許可し、その地点での隣接チェックはスキップする)
- 上記以外で、既に床化済みの別通路タイルに隣接する場合は「並走」として無効と判定する

## 許可する交差と禁止する並走の定義
- **許可**: 通路が既存の別通路のタイルと同一座標を共有して交差する(T字・十字接続)。共有点そのものでの隣接チェックは行わない
- **禁止**: 通路が既存の別通路と同一座標を共有せず、側面(上下左右)だけが触れ合う形で1マス以上並んで伸びる状態
- 回帰テスト(`corridor-contact.test.ts`)にて、直線・L字・T字交差を誤検出しないこと、および意図的な2本の並走ブロックのみを検出することを確認済み

## 代替経路が見つからない場合の処理
- 部屋中心点同士のL字2候補(水平優先/垂直優先)がどちらも無効な場合、各部屋内の中心点近傍の代替接続点(最大4点ずつ)の組み合わせで、上限24回まで代替経路を試す
- MST(部屋を必ず接続するために必要な通路)でこれでも経路が見つからない場合は、その生成試行全体を失敗として扱い、既存の`generateMap`の決定論的再試行ループ(シード+試行回数から再計算)に委ねる。無限探索や無条件の床化・床削除は行っていない
- 追加接続(ループ用、任意)でこれでも経路が見つからない場合は、その1本をスキップするのみとし、生成失敗の扱いにはしない(元々「可能な場合は環状経路を作る」という仕様のため)

# 追記: Section方式による生成器の全面再実装(phase-02-section-map-generator-rebuild)

## 局所的候補経路検証方式(50ed0ae)を不採用とした理由
直前の修正(`50ed0ae`, "fix: prevent unintended corridor adjacency")では、部屋中心同士をマップ全体にまたがるL字で結ぶ既存方式を維持したまま、通路を掘る前に候補経路を局所的に検証する対症療法を実装した。3000シードでの機械的な検証では改善が確認できていたが、その後の目視確認で、部屋配置がマップ全体でランダムに散らばる方式そのものに起因する、通路の不自然な長さ・偏り・接続の読みにくさが残ることが分かった。局所的な検証を積み重ねる方式では、この構造的な問題自体は解消できないと判断し、生成方式自体をSection(区域)方式へ全面的に置き換えることとした。

## 参考資料
- 記事: 「いい感じにランダムで、いい感じに恣意的なランダムダンジョンを生成する」https://qiita.com/kyooooooooma/items/a8ee1157b89b7f744098
- サンプルリポジトリ: RandomDungeonWithBluePrint https://github.com/kyoma0220/RandomDungeonWithBluePrint

上記からは「マップを複数のSectionへ先に分割し、各Sectionに最大1部屋を配置し、部屋のないSectionにはRelay(中継点)を置き、隣接Sectionだけを接続し、Section境界の接続点を経由して通路を作る」という構造上のアイデアのみを理解して採用した。C#コードの記述、クラス構造、変数名、コメント等は一切参照・移植しておらず、rogue-of-sun独自の型・テスト・ゲーム仕様に合わせてTypeScriptで独自に実装した。

## 新しいSection方式
- マップ40×30の内部領域(外周1マスの壁を除く)を3列×3行、9Sectionへ決定論的に分割(端数は先頭のSectionへ配分し、重複・欠落なく分割)
- 各Sectionには最大1部屋を配置(seed付きPRNGで配置数6〜9と配置先Sectionを決定)。部屋を持たないSectionには1点のRelay(中継点、床面積を広げない単一タイル)を配置
- Section同士は上下左右に隣接するものだけを接続対象とし、9ノードの隣接グラフに対してランダム化Kruskal法で全域木を構築後、未使用の隣接辺から1〜2本を追加接続として加える
- 各接続は、部屋の壁面出口またはRelayから自Section側の境界点まで、境界を挟んだ先で隣接Sectionの境界点から相手の出口/Relayまでを、それぞれ自Section内で完結する水平・垂直の直交移動だけで結ぶ(マップ全体にまたがるL字は使用しない)
- 通路生成前に候補経路(水平優先/垂直優先)を検証し、目的の境界交差点以外で既存の通路・部屋と側面接触しないことを確認してから床化する(事後の床削除は行わない)。同一接続の両端経路同士の接触も、境界交差点を除いて検証対象に含めている
- 候補経路がすべて無効な場合は、Section内の代替接続点(最大24通り)を試行し、それでも見つからなければ、必須の接続(全域木相当)はその生成試行全体を失敗として扱い、既存の決定論的な全体再試行ループ(seedは変えず内部試行番号のみ変更)に委ねる。任意の追加接続(ループ用)はその1本をスキップするのみとする

## 初期生成パラメータ
- width:40, height:30, outerWall:1, sectionColumns:3, sectionRows:3
- roomCount:6〜9, roomWidth:4〜9, roomHeight:4〜7, sectionMargin:1(部屋とSection境界の間の余白)
- extraConnections:1〜2, maxGenerationAttempts:50(全体再試行上限), maxConnectionAttempts:20(接続ごとの代替境界点試行上限)

## 接続・通路規則
- 部屋の出口は壁面の中央付近(角を避けて内側にクランプ)に1点のみ配置し、通路を部屋中心まで掘り込まない
- Relayは複数の通路が1点に合流してよく、合流点自体での接触は許可する。合流点以外での通路同士の並走(側面接触)は禁止する
- 通路はSection境界を挟んだ隣接タイル同士でのみ交差し、無関係な部屋の内部を横断しない

## seed互換性を維持しないこと
新しいSection方式は、旧方式(自由配置の部屋中心をL字で結ぶ方式、および直前の候補経路検証方式)とのseed互換性を意図的に維持していない。新方式内では同一seedから完全に同一のタイル・部屋・接続・player/exit/enemy配置が再現されることを決定論性テストで検証している。

# 追記: 1マス幅通路形状の修正(phase-02-one-tile-corridor-geometry-fix)

## 目視確認で見つかった問題
Section方式全面再実装後、seed 2780624551を含む複数シードの目視確認で、部屋外に2×2以上の床塊、部屋境界をまたぐ太い入口、Relay付近での太い接続が発生していることが分かった。従来の検出ロジック(別通路同士の長い側面接触を対象とし、Relayに触れるブロックを一律除外)では、この種の短い2×2床塊を十分に検出できていなかった。

## 既存の並走検出とRelay除外が見逃した理由
- 検出対象が「部屋外かつ別通路同士の長い側面接触」に限定されており、部屋境界そのものに接する短い2×2は対象外だった
- 「Relayに触れるブロックを除外する」例外が広すぎ、Relay周辺で複数通路が2×2的に太くなるケースまで許可してしまっていた
- 経路生成側でも、部屋出口(壁面上の固定軸を持つ点)への接続で、L字の向きを幾何学的な妥当性を考慮せず2通り試すだけだったため、境界点から出口の座標軸に先に揃えてから壁に沿って複数マス移動する向きを選んでしまうことがあった

## 新しい2×2形状制約
4マスの2×2ブロックがすべて床であり、かつその4マスが同一1部屋の矩形内に完全収容されない場合は、原則として禁止と判定する(部屋内部・Relay・別通路・境界跨ぎいずれも例外なく判定。Relayを理由とする一律除外は撤廃)。直線・L字・中心1マスへ収束するT字/十字は、4隅すべてを埋めることがないため誤検出しない。

## 部屋入口とRelayの規則
- 部屋の出入口は壁面上の1マスに限定する。経路構築時、部屋出口(壁面上の固定軸)側は、壁と垂直な軸への移動を経路の最後の1手に限定する、幾何学的に一意な向きを採用するよう変更し、壁に沿った複数マスの接触を構造的に防止した
- Relay側は壁を持たないため、両方の向きを引き続き候補として試行する
- 合流はRelay1点へ収束するT字・十字を基本形とし、2×2床塊はRelay絡みでも一律には許可しない

既存のborder点の決定論的な再試行(接続あたり最大20通り)と、必須接続(全域木相当)が見つからない場合の全体再生成ループ(同一seed・内部試行番号のみ変更)をそのまま維持。追加接続(ループ用)は見つからない場合スキップのみで、無条件の掘削や事後の床削除は行っていない。
